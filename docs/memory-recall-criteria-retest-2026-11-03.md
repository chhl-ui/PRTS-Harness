# 记忆检索判据复测（2026-11-03）

针对 `docs/memory-roadmap-2026-11-02.md` 里三条「已落地但判据未测」的改动，用基准库
`C:/prts-benchmark/memory-s-vec.sqlite`（246,607 turn / 247,428 向量 / 23,854 session）
做实测。全部数字来自本轮工具输出，可复现命令见文末。

**一句话结论**：加权混合在**全量扫描**下达标；但产品现状的 `SEMANTIC_SCAN_CAP = 50_000`
只能看到 19.9% 的 turn 向量，收益在该上限下完全消失（30.9% < bm25 31.8%，p=0.83）。
阅读阶段在 QA 级 A/B 下净收益为 0（10/20 vs 10/20，p=1.0）。

---

## 一、口径校验（先证明探针与历史同源）

`probe-recall-weighted.mjs` 内建两组自检：`[1,0]` 必须复现 bm25 基线、`[1,1]` 必须复现等权混合。

| 配置 | 本轮 @8 | roadmap 记录 | 判定 |
|---|---|---|---|
| bm25 单路 | 75/236 = **31.8%** | 31.8% | ✅ 一致 |
| 向量单路（bge-m3） | 72/236 = **30.5%** | 30.5% | ✅ 一致 |
| 等权 RRF (1:1) | 82/236 = **34.7%** | 34.7% | ✅ 一致 |
| 等权 RRF @32 | **55.5%** | 55.5% | ✅ 一致 |

四组逐字复现 → 后续数字与历史可比。

## 二、判据一：加权混合（全量扫描）——**达标**

判据：`@8 ≥ 34.7% 且 temporal ≥ 60%`。

| 配置 | @8 | temporal@8 | 对 bm25 的 McNemar |
|---|---|---|---|
| bm25 单路 | 31.8% | 64.7% | — |
| 无门控 w 1:0.5 | 35.2% | 52.9% | — |
| **时间词门控 + w 1:0.5** | **36.9%** | **64.7%** | p = 0.0357（显著） |

- **@8 36.9% ≥ 34.7% ✓；temporal 64.7% ≥ 60% ✓ —— 判据成立。**
- 门控把含时间词的 52 题拦回 bm25：`temporal-reasoning` 17 题从混合的 52.9% 完整恢复到 64.7%，
  同时多救回 4 道 `multi-session`（该组 28 vs 混合 24）。
- 配对表：相对 bm25 都中 67、只前 8、只后 20、都无 141 —— 换掉 28 题，净 +12。
- @32 视角更硬：只前 1、只后 14，p = 0.0010（强烈）。

**但**：门控相对等权混合本身不显著（p = 0.3593）。门控的价值在于**救回 temporal**，
不是提高总数——这点必须如实记，别把它写成「比等权更好」。

## 三、判据二（关键）：产品扫描上限下——**不达标**

`src\memory\store.ts:59` 的 `SEMANTIC_SCAN_CAP = 50_000`，查询是：

```sql
SELECT owner_kind, owner_id, vector FROM mem_vectors
 ORDER BY owner_kind, owner_id LIMIT 50000
```

`ORDER BY owner_kind` 是字符串序，`turn` 排在 `fact`/`profile` 之后。实测覆盖率：

| 项 | 数量 | 占全量 |
|---|---|---|
| profile 向量 | 833（全部进 cap） | 100% |
| turn 向量进入 cap | 49,167 | **19.9%**（49,167 / 246,595） |

同一探针加 `SCAN_CAP=50000` 重跑：

| 配置 | @8（全量） | @8（50k cap） |
|---|---|---|
| 向量单路 | 30.5% | **16.9%** |
| 无门控 w 1:0.5 | 35.2% | 30.5% |
| 门控 w 1:0.5 | 36.9% | **30.9%** |
| 门控 w 1:1 | 36.4% | 31.4% |
| bm25 单路（不受 cap 影响） | 31.8% | 31.8% |

- **9 组权重没有一组超过 bm25 基线**，最好的 31.4% 仍低于 31.8%。
- 门控 w 1:0.5 vs bm25：只前 12、只后 10，**p = 0.8318，不显著**（全量时 p=0.0357）。
- @32 的强烈收益也一并消失（p = 0.6250，全量时 p=0.0010）。

**这条比判据一重要**：`fe75437`（Wave 2 语义路上生产，`PRTS_EMBED=1`）在当前库规模下
是**零收益或轻微负收益**。不是算法失效，是产品只喂给算法 20% 的向量。修复前不应把
`PRTS_EMBED=1` 当作已生效能力对外陈述。

## 四、判据三：阅读阶段——**无可判定收益（判据口径本身错配）**

### 先纠一个口径错误

roadmap 写的判据是「multi-session 分型 recall@8 从 27.2% 提升」。这条在阅读层不成立：
`organizeReading` 用 union-find 归组，**不删除、不压缩、不重排命中集合**，
`recall@8` 在数学上不可能因渲染方式而变。拿 recall 测阅读阶段是口径错配。

### 能测的是什么

端到端：同一批命中、「平铺」vs「成卡」两份注入文本，喂同一判分器（DeepSeek，
与 `probe-judge-calib-api.mjs` 同一 prompt，已校准 12/12），配对比较。

| 组 | 可答对 |
|---|---|
| 平铺（旧格式） | 10/20 = 50.0% |
| 成卡（生产现状） | 10/20 = 50.0% |

配对：都中 8 · 只平铺 2 · 只成卡 2 · 都无 8 → **McNemar p = 1.0000**（完全无差异）。

- 20 题里 5 题两份文本逐字相同（命中里没有同主题项可归并）——阅读阶段对它们零作用面。
- 只看真的成卡的 15 题：平铺 7 / 成卡 7，只平铺 2 / 只成卡 2，p = 1.0。

**结论**：结构已就位、零回归（不成卡时输出与旧格式逐字一致，这一点被 5 题同文实测确认），
但**收益未证明**。要判定它必须放大 n 或改用更强判据——n=20 的 ±1 题不可解读是既有教训。

## 五、修复推荐（按优先级）

### P0：让语义路真正看到全量 turn 向量

三选一，推荐第一个：

| 方案 | 做法 | 查询成本 | 代价 |
|---|---|---|---|
| **A. 内存预热（推荐）** | 启动时把 turn 向量全量解成 `Float32Array` 常驻，查询走内存余弦；cap 仅留作降级路径 | 0.25 s/题（本探针实测） | 内存 +1.0 GB |
| B. sqlite-vec / ANN | 引入原生扩展建索引 | 最低 | 新增原生依赖，与「纯 Node」现状冲突 |
| C. 直接抬 cap 到全量 | 改常量 | 每次查询解码 246k BLOB | 每查询秒级，不可用 |

选 A 的理由：本探针就是 A 的形态，已在真库上跑通并给出 36.9%，成本已实测；
且它是唯一不引入新依赖、不改变检索语义的路径。

### P1：把门控加进 `search`

全量扫描恢复后，还需 `TIME_QUERY` 类门控（含时间词的查询只走 bm25），否则 temporal 掉 11.8pp。
正则与判据见 `probe-recall-weighted.mjs`，规则可直接搬。

### P2：阅读阶段维持现状，不追加投入

零回归已验证，收益未证明。在语义路修好、n 放大之前，不再为它加复杂度。

### 不做

- 继续扫权重：50k 下 9 组全负，全量下 1:0.5 与 0.25:1 的差别已落在噪声内。
- 摘要层（`summaries = 0`）：本仓已有实现，但全库需约 27 小时本地推理，
  在 P0 未解决前投入没有意义——候选池残缺时，摘要层只是让残池更整齐。

## 六、embedding 模型不是主瓶颈（k 曲线分解）

问：换个更强的 embedding 模型能否改善召回？

判据：若瓶颈在**模型的语义分辨力**，向量路应表现为「答案在候选池里但排不进前 8」——
即 `vec@32 / vec@8` 明显大于 1，且 `vec@64` 覆盖率接近全体。若大量题在 @64 都找不到 gold，
那是**索引阶段**的问题，任何模型都无效。

实测（236 题，全库 246,595 turn）：

| 类型 | n | vec@8 | vec@32 | vec@64 | @32/@8 |
|---|---|---|---|---|---|
| （全部） | 236 | 30.5% | 49.2% | 59.3% | ×1.61 |
| single-session-user | 64 | 34.4% | 56.3% | 64.1% | ×1.64 |
| multi-session | 125 | 30.4% | 49.6% | 61.6% | ×1.63 |
| single-session-preference | 30 | 10.0% | 30.0% | 36.7% | ×3.00 |
| temporal-reasoning | 17 | 52.9% | 52.9% | 64.7% | ×1.00 |

- **40.7%（96/236）的题，向量前 64 名里一条 gold 都没有**——换什么模型都救不回。
- bm25 同口径 `@64 = 53.8%`，与向量 59.3% 同量级 → 两路都够不到，说明不是模型短板，
  是**索引粒度**：答案跨 turn 分散，单条 turn 的向量与词面都匹配不到整体。
- 天花板：即使把候选池里的 gold 全部完美排进前 8，也只有 59.3%。模型能动的只有
  「@8 → @32 之间那 18.7pp 的排序精度」，且只在 gold 已在池中的 59.3% 上有效。
- 唯一真正「排序受限」的分型是 preference（×3.00），n=30 只占 12.7%——
  即使把它从 10% 提到 40%，总量也只 +3.8pp。

**收益量级对比**（均为 @8，236 题）：

| 动作 | 预期收益 | 成本 | 证据状态 |
|---|---|---|---|
| 修 `SEMANTIC_SCAN_CAP` | **+13.6pp**（16.9 → 30.5） | 改代码 + 1 GB 内存常驻 | 已实测 |
| 换更强 embedding（如 Qwen3-Embedding-4B） | 估 +3~8pp（仅偏好/多会话排序段） | 下载 + 全量重向量化数小时 + 存储 ×2.5 | **推断，未实测** |
| 改索引粒度（session/滑窗 chunk） | 上限 +28.8pp（30.5 → 59.3） | 重建索引 + 迁移 | 未做 |

结论：换模型不在第一顺位。**cap 修复的收益是换模型的 2–4 倍、成本低一个数量级**；
剩下 40.7% 的结构性空洞只能靠索引粒度解决。

若要实测换模型，最小成本方案：抽 50k turn（含全部 gold）+ 两模型同样本对比，
约 1 小时，足以判定偏好/多会话分型的排序增益。

## 七、索引修复与其产品口径实测（`a8ac8fa`）

按第五节 P0 方案 A 实现：`MemVectorIndex` 把 `mem_vectors` 全量解码进 `Float32Array`，
`store.search` 的语义段在索引就绪时走内存全量余弦，否则降级原 SQL 路径（cap 语义保留）。

端到端（`probe-index-e2e.mjs`，236 题，走真实 `store.search`）：

| | @8 | |
|---|---|---|
| 未预热（cap 50k） | 72/236 = **30.5%** | |
| 预热后（247,428 条全量） | 80/236 = **33.9%** | 配对 只冷 8 / 只热 16，**McNemar p = 0.1516** |

预热成本 3.4 s / 247,428 行 / dim 1024。分型：user 42.2→46.9、multi 27.2→31.2、
preference 3.3→3.3、temporal 58.8→58.8。

### 参数不是瓶颈

`probe-index-tune.mjs` 扫四组产品参数（236 题，产品口径）：

| 配置 | @8 |
|---|---|
| minSim 0.25 / topK 15（当前生产） | 80/236 = 33.9% |
| minSim 0 / topK 15 | 80/236 = 33.9% |
| minSim 0 / topK 64 | 80/236 = 33.9% |
| minSim 0.25 / topK 64 | 80/236 = 33.9% |

四组两两 McNemar p = 1.0000。`minSim` 0.25→0 时**零题变化**（只前 0 / 只后 0）；
`topK` 15→64 是 11/11 互换、净 0，只是换了命中的题（multi-session +3pp、temporal −6pp）。
放宽这两个旋钮拿不到任何总量收益，**不要动它们**。

### 与 36.9% 的差额是口径差异，不是产品缺陷

33.9%（产品 `store.search`）与 36.9%（`probe-recall-weighted.mjs` 手工融合）**不可直接比**：

- 36.9% 是在「只对 turn 排序、按 turn 相对名次判 @8、bm25 候选池 64 条」的口径下得到的；
- 33.9% 是产品真实返回（多路 FTS + 语义融合、按绝对名次判 @8、候选池 `limit × 3`）。

已排除「fact/profile 命中挤占前 8」这一嫌疑：抽 40 题实测，前 8 名里非 turn 命中 **0 题**，
gold turn 被挤出绝对前 8 的也是 **0 题**。差额来源未完全定位（候选池深度与题集口径都可能是），
但**不影响结论方向**：索引修复是真的（多救 16 题），幅度只有 +3.4pp。

### 下一步该做什么

1. 按 k 曲线（第六节），真正的天花板在**索引粒度**：40.7% 的题前 64 名无 gold，
   这只能靠 session/滑窗 chunk 或摘要层解决，与向量模型、cap、融合参数都无关。
   注意 v2.11 的「session 两阶段粗筛」已被实测否决（38.8% → 34.0%），不要重走。
2. `PRTS_EMBED=1` 现在需要配合预热才有意义——`start.ts` 已在该开关下自动预热。

## 八、reranker 是当前性价比最高的一步（+8.9pp，p=0.0008）

问题：「除了 bge-m3 还有别的模型方案吗」。先看天花板再选型——k 曲线已把缺口切成两段：
40.7% 的题前 64 无 gold（索引粒度问题），剩下 59.3% 里才是排序问题。
**reranker 正好打后一段**，且不需要重建任何索引。

### 实验（零下载：两个 reranker 都已在本地 HF 缓存）

`probe-rerank-export.mjs` 导出 236 题的 32 条候选（`store.search` 产品口径，预热索引），
`probe-rerank.py` 用 CrossEncoder 对 `(question, 候选正文)` 成对打分重排。

| reranker | 参数 | @8 | 配对 | McNemar | CPU 延迟 |
|---|---|---|---|---|---|
| （原始融合排序） | — | 80/236 = 33.9% | — | — | — |
| bge-reranker-base | 278M | 101/236 = 42.8% | 只原 8 / 只新 29 | p = 0.0008 | 1.57 s/题 |
| **ms-marco-MiniLM-L-6-v2** | **22M** | 105/236 = **44.5%** | 只原 4 / 只新 29 | **p = 0.0000** | **0.24 s/题** |
| bge-reranker-v2-m3 | 568M | 103/236 = 43.6% | 只原 8 / 只新 31 | p = 0.0003 | 5.74 s/题 |

**三个模型都显著，但参数量与效果反相关**：22M 的 ms-marco 最好（44.5%），568M 的 v2-m3
只有 43.6%，且慢 24 倍。原因不难理解——ms-marco-MiniLM 是专门为英文 passage reranking
训练的，而 bge-reranker-v2-m3 是多语言通用模型，为跨语言场景做了取舍。这条直接否掉了
「换更大的模型会更好」的直觉：**在这份数据上，任务匹配度比参数量重要**。

分型上两者各有胜负：v2-m3 在 single-session-user 上 60.9%（ms-marco 57.8%），
但 multi-session 只有 42.4%（ms-marco 44.8%），temporal 两者都不动（52.9%）。

两个独立模型都大幅提升、都显著 → 增益来自 rerank 机制本身，不是某个模型的偶然；
且**小 12 倍的模型反而更好**（它是专门为 passage reranking 训练的）。


- 候选池内存在 gold 的题 **121/236 = 51.3%**（rerank 的理论上限）。
- 池内有 gold 却排不进前 8 的 41 题里，两个模型都**救回 29 题（71%）**。
- 分型（ms-marco 口径）：multi-session 33.6→44.8（+11.2）、single-session-user 43.8→57.8（+14.0）、
  preference 3.3→6.7（+3.4）、temporal 52.9→58.8（+5.9）。

### 与其它方案的收益对比（同一 236 题口径）

| 方案 | @8 变化 | 成本 | 状态 |
|---|---|---|---|
| **reranker（ms-marco-MiniLM-L-6-v2）** | **33.9 → 44.5（+10.6pp）** | CPU 0.24 s/题，零下载 | **已实测，p=0.0000** |
| reranker（bge-reranker-base） | 33.9 → 42.8（+8.9pp） | CPU 1.57 s/题，零下载 | 已实测，p=0.0008 |
| 修 `SEMANTIC_SCAN_CAP`（已落地） | 30.5 → 33.9（+3.4pp） | 1 GB 内存 / 3.4 s 预热 | 已实测，p=0.15 |
| 换 embedding 模型 | 估 +3~8pp | 全量重向量化数小时 + 存储 ×2.5 | 未实测 |
| 索引粒度（session/滑窗 chunk） | 上限 +17.4pp（33.9 → 51.3） | 重建索引 + 迁移 | 未做；v2.11 session 粗筛已被否决 |

**结论：先做 reranker，不要先换 embedding 模型。** 它收益最大、代价最小、证据最强，
而且与索引粒度改造不冲突——两者分别打后一段和前一段缺口。

### 产品化的取舍（未做，需决策）

- 延迟：ms-marco 在 CPU 上 0.24 s/轮（32 对），可接受；bge-reranker-base 1.57 s 偏慢。
- 候选深度：本实验用 32 条。生产 `limit = 5`，若 rerank 前先扩到 16–32 条再取前 5，
  延迟与上下文占用需一并评估。
- 依赖：Ollama 不提供 rerank 接口，必须走 Python（sentence-transformers）或 ONNX。
  这与 PRTS「Node 单栈」的现状冲突，是产品化前要拍板的地方。
- 本机 torch 是 CPU 版（`2.14.0+cpu`）；要 GPU 加速需另装 CUDA 版 torch。


### sparse / colbert 两条路（bge-m3 的另外两种输出）

bge-m3 一次前向产出三种表示，PRTS 只用了 dense（Ollama `/api/embed` 只返回 1024 维稠密向量）：

| 输出 | 形态 | 取法 | PRTS 现状 |
|---|---|---|---|
| dense | 1024 维向量 | 已在用 | ✅ 生产 |
| sparse | `dict[token_id → 权重]` | `FlagEmbedding` `return_sparse=True` | ❌ 无 |
| colbert | token 级多向量 | `return_colbert_vecs=True` | ❌ 无 |

实测（本机 FlagEmbedding + bge-m3 2.14 GB，CPU）：

```
query "what camera do I use" → 5 个 token，最高权重 0.318
vs "I shoot with a Sony A7 IV camera body" → 0.0824
vs "I drink tea every morning"             → 0.0188
vs "My daughter plays piano"               → 0.0000
```

排序正确，但分值极低——**sparse 依赖精确 token 重叠**，问句与陈述句共享的 token 通常只有一两个。
机制上与 bm25 同类（区别只在权重是学出来的而非 IDF），因此它攻的正是 bm25 已经较强的词面领域。

**成本是决定性的**：已有 24.6 万条 dense 拿不到 sparse，必须重新 encode。
本机实测吞吐约 11 条/秒（模型加载 133 s 不在内）→ 全量约 **6 小时**，比当初 Ollama 跑 dense 的
44 分钟慢 8 倍（FlagEmbedding 在 CPU 上没有 Ollama 的批处理与量化）。

结论：sparse 不在优先队列。要验证也应走最小口径——抽 20 题、题内、只算 query 侧 sparse
与候选池的重叠，1 小时可判趋势，不必全量重算。
