# 注入层端到端评测（P0，2026-11-02）

回答一个问题：**自动注入有没有把检索到的证据真的送到模型面前，那些证据够不够答对。**

---

## 方法（以及为什么不用真 LLM 跑完整链路）

DSH 的 LLM 适配器不支持自定义端点（`config/prts.yml` 的 `llm-deepseek` 只有
apiKeyEnv / contextWindow / idleTimeout），要换成本地 27B 得改写 adapter。所以把问题拆成两层分别测：

| 层 | 怎么测 | 成本 |
|---|---|---|
| **A 注入层** | 真实 `startRuntime` + 真实 `agent/pre-step`，脚本化模型只负责结束回合；旁听器（`prepend: true`，最外层）捕获最终注入文本 | 零模型、零 key |
| **B 内容质量** | 把捕获到的注入文本 + 原问题交给本地 27B 判分（与 `probe-judge-calib.mjs` 同一 prompt，已校准 12/12） | 本地推理 |

每题**独立 dataRoot**：真机探针发现同一 dataRoot 下不同 sessionId 会串会话历史，
不隔离的话第 n 题能看到前 n-1 题，结果全废。

抽样：按题型轮转取 20 题（6 个题型各 3–4 道），避免前 N 条全是 `single-session-user`
——交接文档记过这个坑（前 50 条同型导致「−8pp 反转成 +4.8pp」）。

复现：`node --disable-warning=ExperimentalWarning .rivet/scratch/probe-e2e-injection.mjs 20`

## 结果

| 指标 | 数值 |
|---|---|
| 注入发生 | **20/20** |
| 有注入时可答对 | **14/20（70.0%）** |
| 无注入时可答对 | 0/20 |
| 净增益 | +14 题 |

分型：

| 题型 | 可答对 |
|---|---|
| knowledge-update | 3/3 |
| single-session-assistant | 3/3 |
| single-session-user | 3/4 |
| temporal-reasoning | 2/3 |
| multi-session | 2/4 |
| single-session-preference | 1/3 |

## 三条必须说清的限定

### 1. 这是**题内口径**，不能与全库 `any@8 = 32.8%` 直接比较

每题只导入该题的 haystack（约 480 turn），而全库口径是 246,607 turn。
交接文档记过同一个口径混淆（题内 bm25 = 93.6% vs 全库 = 20.4%）。
70% 介于两者之间是合理的：题库里有大量干扰 session，但远小于全库。

**能说的**：在「记忆库里只有这道题的相关对话」时，注入的 top-5 有 70% 足以答对。
**不能说的**：生产全库下也是 70%。

### 2. 对照组是结构性无效的

`无记忆判=0/20` 不能解读为「没有记忆就一定答不对」——判分 prompt 问的是
「给定下面这些记忆，能否写出满足 rubric 的答案」，喂空字符串必然判 no。
这个 0 是设计使然，没有信息量。

有效的对照应该是「检索到了但 top-k 未包含 gold」，本轮没做。

### 3. 失败样本的分布有指向性

失败的 6 题集中在 `multi-session`（2/4 失败）、`single-session-preference`（2/3 失败）。
后者与 30 题画像评测的结论一致：`06878be2` / `75832dbd` 在那一轮的三组里也全是 n
——说明这两题是检索层的稳定失败，不是随机波动。

---

## 结论

1. **注入层是通的**：20/20 全部注入成功，且注入内容里确实有可用证据。
2. **证据质量不是瓶颈（在题内口径下）**：70% 的题，注入的 top-5 已足以答对。
3. **全库口径仍是未知**：要在生产规模下评估，需要把评测搬到 24.6 万 turn 的库上，
   或者引入分层噪声。
4. **preference 与 multi-session 是稳定弱项**，与既有基线一致，不是本轮引入的。

## 全库口径（同日追加，已执行）

题内口径（每题只导入该题 haystack，约 480 turn）测不出真实规模的影响。补一轮全库：
**同一批 20 题 + 真实 `memory-s.sqlite`（246,607 turn）**。

做法：复制真机库到临时目录，把 turn 的 `origin` 由 `benchmark` 改标 `live`
（注入器写死只读 live，设计稿 §6.4；原库一个字节没动），再走与题内口径**完全相同**的
注入链路与判分器。复现：`.rivet/scratch/probe-e2e-fullcorpus.mjs`。

| 口径 | 注入发生 | 注入可答对 |
|---|---|---|
| 题内（约 480 turn/题） | 20/20 | **14/20（70%）** |
| **全库（246,607 turn）** | 20/20 | **10/20（50%）** |

分型对比：

| 题型 | 题内 | 全库 | 差 |
|---|---|---|---|
| knowledge-update | 3/3 | 1/3 | **−2** |
| single-session-assistant | 3/3 | 2/3 | −1 |
| single-session-user | 3/4 | 2/4 | −1 |
| multi-session | 2/4 | 2/4 | 0 |
| temporal-reasoning | 2/3 | 2/3 | 0 |
| single-session-preference | 1/3 | 1/3 | 0 |

**规模衰减主要集中在 knowledge-update**（−2）。这与该题型的语义一致：它要求「最新值」，
而全库里有大量旧版本信息参与竞争，top-5 更容易被旧值占满。其余题型在全库下没有额外损失。

检索耗时（全库、单次注入）：**407–1937 ms，中位约 0.9 s**。交互式对话可接受，
但如果每轮都跑，需要知道这是每题一次的固定开销。

### 与 `any@8 = 32.8%` 的关系

**不是同一个指标，不能相减。** `any@8` 问「top-8 里有没有 gold turn」；
本评测问「top-5 的内容够不够写出满足 rubric 的答案」。判分器比 turn 级命中宽松
（它允许把多条证据拼起来），所以 50% > 32.8% 不可解读为「注入比检索多 17pp」。

要得到严格可比的数字，得在注入口径下重跑 250 题并同时记录 any@k——本轮没做。
