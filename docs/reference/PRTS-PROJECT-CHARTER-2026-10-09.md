## 一 项目总目标

建设一个由博士持续使用、能够理解任务、保留有效记忆、调用实际工具、执行长期工作并交付可核查结果的 PRTS。系统以个人电脑为主要入口，按任务需要连接本地与远程模型、资料、专业软件、计算资源和授权设备，在科研与日常工作之间共享一致的任务、知识和权限体系。

PRTS 的完成标准是博士能够把一项具体工作交给它，在必要的选择与授权之后，得到可用的成果、真实的执行状态和足以检查结论的依据。遇到信息不足、工具失效或能力边界时，它应说明原因、保存进度并提供可执行的恢复路径。

明日方舟中的 PRTS 提供产品愿景：持续陪伴、信息终端、决策辅助、任务代理、科研支持与系统管理。现实项目将这些愿景转化为可测试的能力。界面、称呼、语音和人格服务于长期使用体验；研究与执行质量由独立证据判断。

本目标书以最终产品目标为准。DSH、现有研究引擎、插件、存储结构和界面均为候选实现，可以保留、拆分、替换或重建。既有架构的限制不得自动缩减产品目标；已投入的工作量也不能单独成为保留理由。

本次立项文件允许重新设计实现路线，不自动触发删除数据、停用服务、迁移生产资产或扩大设备权限。现有工程规则在对应工程实际变更前继续适用；需要替代时，必须明确后继规则、迁移证据和回退办法。

## 二 用户结果与典型工作

项目当前服务一位主要用户。多用户租户、商业运营和公共服务不作为首版交付前提。跨电脑、移动端和远程访问保留在完整产品范围中，按真实使用价值排期。

### 1 科研工作

博士给出研究问题、已有资料和约束，PRTS 能完成文献检索与归纳、数据检查、方法选择、代码或实验方案编制、计算与仿真、结果比较、图表与报告生成。每个关键结论能区分文献事实、实验观测、程序计算、模型推测和待验证假设。

典型任务：给定一组实验数据与若干参考文献，检查数据质量，选择适当方法，运行分析，与独立基准比较，输出报告及复现材料；第二天继续时能定位原始数据、参数、代码版本和未完成工作。

科研能力面向多学科扩展。光学是现有资产较多的验证场景，不能成为核心系统的隐含前提。统计分析、数值计算、符号计算、仿真、实验设计、机器学习和专业软件接入，应按统一的能力描述与结果证据接入。

### 2 个人日常工作

博士通过文字或语音交代工作，PRTS 能检索个人资料、整理文件、制作文档或表格、维护任务与日程、执行重复事务，并在约定条件下主动提醒。任务中途退出应用或切换话题，不应导致工作丢失或重复执行。

典型任务：从授权目录找到会议资料，整理为简报和待办，识别时间冲突，生成日程变更预览，在已有授权范围内执行，并在下次交流中说明哪些完成、哪些仍等待外部条件。

### 3 持续运行与管理

PRTS 能管理长计算、资料更新和设备状态监测，按约定频率运行，只在结果变化、失败或需要博士决定时通知。能说明正在消耗哪些资源、已经执行什么、为什么暂停，以及停止后还会不会继续产生效果。

## 三 完整产品能力范围

下表是最终目标，不等于当前已具备的能力。每一项最终都须有真实端到端任务、失败用例和用户验收；仅安装软件、展示工具菜单或完成单次演示不构成交付。

|---|---|---|
| C01 | 统一交互与任务上下文 | 文字、语音及图像或文档输入能进入同一任务；能切换话题、打断、纠正与继续，任务状态可见 |
| C02 | 信息终端与个人知识库 | 能从授权的本地资料及外部来源检索答案，定位原文，处理新旧版本、冲突、撤回和更新 |

| C04 | 理解与决策辅助 | 将目标转成可执行步骤，识别缺失信息，比较方案及成本，处理不确定性并解释重要选择 |
| C05 | 工具使用与工作执行 | 操作文件、程序、浏览器及授权应用；有输入校验、执行记录、结果核验、重试和恢复机制 |

| C07 | 个人事务与成果制作 | 文件整理、文档与表格制作、日程和待办、周期事务、资料归档能形成可直接使用的交付物 |
| C08 | 任务与资源调度 | 支持前后台任务、优先级、依赖、并发限制、预算、检查点、取消、恢复及完成通知 |
| C09 | 设备与环境控制 | 在已声明的权限内读取或控制电脑外设、局域网设备与智能家居，并核对真实状态反馈 |
| C10 | 情报分析与运行维护 | 对授权数据源和自有或获授权网络进行采集、日志分析、异常检测和维护；报告可定位原始事件 |
| C11 | 权限 安全与运维 | 管理账户、凭据、数据出境、工具权限、审计、备份恢复与升级回退；提供异常和资源状态面板 |
| C12 | 能力扩展与持续改进 | 能发现、评估和接入新工具或专业模块；新能力通过测试后发布，升级可比较、可回退 |

通用能力的方向是逐步减少为每个任务手写流程的需要，并通过未知任务评估检验迁移能力。AGI、自主意识、无限可靠预测和无人监督的全学科科研突破不作为可承诺的项目验收指标。完整产品仍以明确支持范围和可重复结果接受验收。

## 四 首个可交付版本

首版必须同时跑通科研和日常工作，两者使用同一套任务状态、资料来源、成果存储与权限机制。科研模块完成而日常工作仍停留在聊天，或日常助手完成而科研只能给建议，都不能算首版完成。

首版包含：

1. 统一文字入口，支持附件、图片理解、任务状态、历史检索和继续工作。
2. 可引用原文的知识检索，以及可查看、纠正和删除的偏好与项目记忆。
3. 文件、命令行和至少一种实际应用操作通道；工具失败与模型回答必须明确区分。
4. 科研主流程：资料与数据导入、计算或仿真、独立结果检查、图表和报告、复现包。
5. 日常主流程：资料整理、文档或表格交付、任务与日程管理、周期提醒。外部日历未接入时可先提供本地日程，但不得将本地记录表述为外部同步成功。
6. 后台任务、预算限制、取消、恢复、进度与必要通知。
7. 文字与语音指令切换，按键说话、语音播报和停止播报。常驻唤醒词、嘈杂环境远场拾音可在后续完成。
8. 执行权限、凭据保护、数据流向说明、备份恢复、故障诊断和导出迁移。

首版科研至少覆盖两个可实测场景：一个通用数据分析场景，一个工程计算或仿真场景。二者必须真正产生成果，不能以两个名称指向同一演示任务充数。具体学科由真实任务和可用工具决定。

设备控制、多终端访问、自动化网络维护和大范围专业软件扩展属于后续完整产品阶段。它们仍在最终范围内，不因首版未实现而删除。外发消息、外部提交和设备写操作遵守用户已给定的授权范围，不将拟定计划自动解释为执行授权。

## 五 产品行为与质量原则

### 1 以任务成果衡量价值

任务需要有目标、输入、输出、验收方式、执行范围和资源预算。PRTS 应区分已完成、部分完成、等待输入、等待授权、失败和取消。只有成果通过相应检查才能标记完成，模型说“完成”不能改变执行事实。

### 2 自主执行与人类控制并存

普通可逆工作在授权范围内连续推进，不要求博士逐步确认。信息不足且影响结论、权限不足、超出预算或不可逆效果未获授权时，应说明具体原因并只暂停相关步骤。停止指令必须立即禁止新的相关副作用；已经提交到外部系统的动作，明确报告是否能够撤销。

权限应有任务或会话范围、有效期与撤销入口，必要时可以形成长期授权。权限判定必须发生在工具执行入口，不能只靠提示词。模型不能为自己签发授权。架构调整必须保留或提供经过验证的等效控制。

### 3 知识 记忆与人格分开管理

原始资料保存出处、版本与时间；工作记忆保存项目状态及依据；个人偏好保存确认情况与适用范围；人格控制称呼和表达。推断的偏好不得冒充用户明确要求，旧记忆不得覆盖当前证据。

用户可以纠错、停用和删除个人记忆。删除应覆盖检索索引与派生摘要，并说明备份保留策略；科学回执和历史研究记录按既有留存规则处理，以后继证据注明失效或更正，不能为了统一记忆功能而悄悄改写。

### 4 科研可靠性独立于语言流畅度

计算必须保存输入数据、单位、方法、参数、环境与结果来源。随机过程记录种子与容差。采用解析解、已知基准、独立实现或独立实验等方式检查关键结论，不能以同一程序重复执行或另一个模型表示赞同代替验证。

模型生成的解释与计算输出分别记录。无数据支持的推断明确标为假设；无原始来源的引用不得出现在正式交付中。失败的试验和不支持预期的结果也必须保留。

### 5 可恢复 可迁移 可维护

任务状态与重要产物持久保存，恢复不能依赖一段聊天摘要。重试必须识别已产生的效果，无法判断时先核对外部状态，不能直接重复提交。系统需支持健康检查、故障定位、版本固定、升级比较和回退。

核心数据可导出为公开描述的格式。模型、运行框架、界面或存储实现更换后，知识来源、任务历史、研究证据和有效权限仍能被解释；不能迁移的内容必须列明并有处置方案。

## 六 验收指标与测量方法

本节数字是本目标书提出的产品目标，不是已测性能。测试数据集、硬件、模型版本、网络条件和预算在相应阶段开始前冻结。未达到指标时保留失败，不得事后删除困难样本或改变分母以获得通过。

### 1 首版验收

| 编号 | 指标与门槛 | 验证方法 |
|---|---|---|
| A01 | 60项端到端任务，科研30项、日常30项；总成功率至少85%，每类至少80% | 各类至少10项在实现前不向开发过程公开；按冻结的成果标准由用户或独立检查者判定；所需人工接管计入失败 |
| A02 | 50项关键事实检查，证据支持正确率至少95%；全部正式引用可定位原文 | 从交付物抽取事实，由原文逐项核对；捏造文献或实验结果为发布阻断项 |
| A03 | 40项记忆用例至少90%正确；10项纠错或删除用例全部通过 | 跨新会话和重启测试；检查事实冲突、时间范围、来源和派生索引，不只看回答措辞 |

| A11 | 完成一次完整备份恢复和一次核心组件替换演练 | 逐项核对任务 数据 记忆 研究证据；统计迁移差异，不允许静默丢失；替换至少涉及模型或执行适配器 |
| A12 | 连续14天试用完成至少50项真实任务，科研与日常各不少于20项；无未关闭的发布阻断项 | 日志记录成功 失败 接管时间与恢复结果；与不少于10项同类人工基线比较，人工主动操作时间中位数降低至少30% |

指标补充口径：成功任务必须产生符合约定的成果。合理拒绝仅在专门的拒绝用例中计为通过，不能充当普通任务成功。用户按流程给出必要信息或授权不算接管；用户替系统修代码、改产物、重复执行或手工恢复才算接管。

样本通过只说明在该测试范围内成立，不能宣称绝对安全或普遍可靠。原始执行记录、评判依据、失败明细与环境信息须保留。发布阻断项包括数据损坏、越权效果、凭据泄露、科研结论造假、不可解释的重复提交以及无法恢复的已确认成果丢失。

### 2 完整产品验收

C01至C12逐项完成，每项至少有5个正常用例和3个失败或边界用例，允许复用同一任务中的不同检查，但需有逐项对应的证据。科研与日常两类核心任务继续满足首版门槛。

设备控制至少覆盖两类获授权设备，检查指令回执与实际状态一致；运维能力至少覆盖三类故障的检测、定位、受控处置与恢复。网络检查只在声明的自有或获授权范围进行。

新增一个此前未接入的专业能力，通过公开接口接入并完成真实任务，证明系统扩展不依赖改写核心流程。至少完成一次运行框架或任务执行服务的替换演练，保留资料、任务历史与可验证产物。

完整产品需连续30天使用并完成至少100项真实任务，两类核心工作各不少于30项，所有能力有使用或专项验收记录，无未关闭发布阻断项。博士确认它能够作为日常主工作入口后，才宣布达到本期完整产品目标；新增需求进入后续版本。

## 七 架构选择与重建原则

当前不把 DSH 定为不可替换的产品核心。它具有现成运行环境和接入资产，应作为架构验证的首个候选；是否继续承担核心调度，由真实任务与替换成本决定。

架构候选必须覆盖三种路线：在现有 DSH 上扩展；让 DSH 负责交互与模型调用而由独立服务管理任务和资产；更换运行框架或重建必要核心。三条路线使用同一组科研、日常、恢复和权限测试，不能仅比较界面或插件数量。

先检查硬门槛：关键权限可执行、任务与数据可导出、失败可定位、成果可复现。通过硬门槛后，按任务完成质量30%、恢复与可运维性20%、数据与执行可控性20%、扩展及迁移成本15%、日常体验与运行成本15%评分。成本包含实际维护工时和资源费用，不只计算模型单价。

达到门槛且得分最高的路线优先；差距小于5分时，选择验证成本更低、迁移更简单的路线。若没有候选通过硬门槛，应先补足缺陷，不能宣布选型完成。

重建时可以淘汰代码与旧接口，但必须先盘点数据、凭据引用、资料原件、研究回执和有效工作流。新旧系统经过并行核对与恢复演练后，再切换默认入口。需要重新计算的旧研究明确标识；旧证据按原版本保留，不伪装为新系统产生。

模块名称、进程数量、编程语言、数据库和多智能体数量均留给后续架构设计。若单智能体更可靠，就采用单智能体；引入并行执行须证明它改善完成时间或质量，并处理共享状态冲突。
