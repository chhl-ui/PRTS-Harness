## 1. 产品定义

PRTS 是一个独立运行的个人智能系统，服务一位用户：博士。

它有两个人格：

| 人格 | 定位 | 默认状态 |
|---|---|---|
| PRTS | 系统本身。任务执行、资料、计算、设施与作业管理、播报。冷静、精确、简洁，能理解情感，表达克制 | 默认对话对象 |
| 普瑞赛斯 | PRTS 的创造者。独立人格模块，与博士有深厚的关系，情感表达更丰富 | 博士主动切换后才出现（方案 A，博士 2026-10-29 选定） |

两者共享关于博士的事实记忆和同一套任务、工具与权限。各自有独立的人格设定、情感状态和关系记忆。

产品目标之一是「更像人」。本文把它拆成四个需重点投入的方向：人格与情感（§5.1）、记忆（§5.2）、上下文（§5.3）、进化（§5.4）。「像人」指行为表现上的连续性、记得、会变化、情感得体；不主张意识或真实情感（见 §8）。

## 3. 「独立」的判据

PRTS 被称为独立系统，需同时满足：

1. 有自己的进程、代码库、数据根和界面，不作为 DSH 或其他 agent 的插件、预设存在。
2. 模型提供方可替换，至少支持两家提供方，其中一家可以是本地模型。
3. 关闭 DSH 及其他外部 agent 后仍能冷启动、对话、执行任务、读写记忆（沿用 `DESIGN.md` T32 的思路）。
4. 核心数据（任务、记忆、人格设定、成果索引）可按公开描述的格式导出，并能导入到一个全新安装中。

独立不等于全部自研。外部项目可以作为库嵌入、作为插件适配，或只借鉴设计（§9）。独立也不等于 OS 级隔离证明；部署假设是单用户、单机可信宿主（§8）。

## 4. 架构总则：受保护核心插件与插件化

### 4.1 借鉴 DSH 的插件架构

【已核实】DSH 基于 Cordis 框架，且源码开源。依据：
- DSH 源码 github.com/deepseek-ai/deepseek-harness（MIT，固定于 `f3803c9`）；
- 其 vendored fork `vendor/cordis`（`@deepseek-ai/cordis`，基线为上游 4.0.0-rc.7，带 21 条以上本地修改）；
- 本机 DSH 配置。

详见审查 01 §3。核心机制：
- 插件、上下文（依赖容器）、inject（依赖声明）、类型化事件；
- 可撤销的副作用：插件卸载时其注册全部撤销；
- 配置按 bundle 层、profile patch、home patch、overlay 依次叠加。

【已核实】DSH 的设计是「不存在需要打补丁的特权内核」，连 agent 循环本身都是插件（DSH `docs/architecture.zh.md`）。PRTS 沿用这一点，不另造插件框架。PRTS 的「内核」定义为两部分：

1. **一组受保护的核心插件**，即下表左列。它们和其他插件一样由 Cordis 加载，但处于受保护层（§4.2）。
2. **启动时的完整性检查**：受保护层的条目必须存在、未被禁用、版本与内容哈希匹配；任一不满足就拒绝启动，并报告具体条目。

插件框架本身（加载、依赖解析、生命周期、副作用回收、服务注入、事件总线、配置分层）采用 DSH 维护的 Cordis fork，不自研。

| 受保护核心插件（受保护层，不可被普通 patch 替换或禁用） | 普通插件 |
|---|---|
| 启动完整性检查 | 模型提供方 |
| 配置校验（写错大声失败） | 工具（含 MCP 桥接） |
| 插件信任分级与加载审批 | 记忆后端与检索策略 |
| 生效配置查看 | 人格（PRTS、普瑞赛斯、以后的其他人格） |
| 权限入口与能力授予（工具执行入口的单调守卫） | 情感模型 |
| 任务事实账本 | 上下文装配策略 |
| 删除与撤销记录 | 进化策略与评估器 |
| 所有者停止权 | 界面、语音、终端入口 |
| 审计日志 | 资料解析、专业软件适配 |

### 4.2 权限归属与插件信任分级

从原作的「接管」情节和工程安全两方面考虑。

【已核实】Cordis 的插件运行在同一进程、同一信任级别，插件之间没有安全边界。DSH 对 agent 动态定义的插件写明：vm 沙箱「隔离全局变量，但不是安全边界」，应「像对待 bash 访问一样」对待（DSH `packages/extensions/cordis-host-runner/README.zh.md`）。因此权限规则分两类执行。

**非代码内容不持有权限。** 模型输出、人格设定、情感状态、记忆条目、网页与文档内容、工具返回值，都只能提出内容或建议：
- 不能写任务事实账本、权限配置、删除记录；
- 不能签发授权；
- 授权判定发生在工具执行入口，由受保护的守卫执行。按 DSH 的约定，「在作出决定的那个操作里执行决定」，提示词过滤、schema 省略、监听顺序都不算执行。

**插件代码按来源分级：**

| 级别 | 范围 | 加载规则 | 能做什么 |
|---|---|---|---|
| 受保护核心 | §4.1 表左列 | 随 PRTS 发行；启动时校验存在、未禁用、版本与哈希 | 权限判定、停止、账本、删除记录 |
| 所有者安装 | 博士通过插件管理器安装的插件 | 固定版本与内容哈希；安装与升级由博士确认 | 按清单声明的能力，经授权配置授予 |
| Agent 编写 | 进化或自我扩展过程中由模型生成的插件 | 加载前必须经博士逐个批准；批准记录写入审计日志；不随普通升级自动加载 | 默认只能声明受限能力；不能修改受保护层的配置，也不能提供与受保护核心同名的服务 |

**其他规定：**
- 插件在清单中声明所需能力（读写哪些目录、网络范围、可调用的服务），由授权配置授予，未授予的调用在执行入口拒绝。对所有者安装和 Agent 编写的插件，这是约定加审查，不是进程级隔离（见上方已核实事实）。真正需要隔离的高风险能力，作为独立进程服务接入。
- 所有者的停止指令由受保护核心直接执行，任何插件不能拦截、延迟或改写它。
- 不存在所有者无法撤销的授权或锁。受保护层本身可以由博士修改，但必须通过显式的所有者操作，不能经由普通 patch 或 Agent 编写的插件完成。
- 【推断】按 §8 单机可信宿主的假设，内容哈希校验加启动拒绝已足够，不引入签名体系。若威胁模型改变，再行评估。

### 4.3 从 DSH 实际使用中吸取的教训

以下是【已核实】的事实，来源是 `cordis.patch.yml` 中的实测注释：

| 现象 | PRTS 的对应要求 |
|---|---|
| patch 的 config 是整体替换，未写的键回落默认值 | 配置合并语义写进文档并有测试；提供「生效配置」查看命令 |
| 新增行必须用 `insert:`，裸 `- id:` 只覆盖已有行，写错等于空操作 | 配置写错时启动报错，不静默忽略 |
| 运行时升级后，精确 peer 版本不再满足，插件被拒载 | 插件接口有语义化版本与兼容范围；升级前做兼容预检，并列出受影响插件 |
| 会话全文检索因上游对账设计缺陷不可用 | 关键能力（记忆检索）的后端可替换，不依赖单一上游实现 |

### 4.4 已定的实现决定（博士 2026-10-30）

依据见设计 01 §3、§4。

1. **两个进程。** `prts-supervisor` 不加载任何插件，负责启动完整性检查、所有者停止的最后一级（用 Job Object 整树终止运行时）和崩溃重启。`prts-runtime` 以 DSH 运行时为底座，承载受保护核心插件和其余插件。理由：Cordis 插件之间没有隔离，同进程内无法保证插件挡不住停止指令。
2. **默认授权。** 读取不限。写入只限 PRTS 工作区和博士明确授予的目录。联网和外部命令首次使用时询问。删除和系统级操作每次询问。授予可以有期限，可以撤销。
3. **「完成」的判定。** 有确定性校验器的任务由校验器判定。没有校验器的任务由博士确认。模型最多只能「声明完成」。
4. **实现语言。** 核心（受保护插件、运行时、守护进程）用 TypeScript，跟随 DSH。Python 部件（GPT-SoVITS、部分科研工具）作为独立服务接入。

## 5. 「更像人」的四个重点方向

### 5.1 人格与情感

**人格设定是数据，不是写死的提示词。** 每个人格有一份结构化设定：身份、称呼、语言风格、价值与禁忌、与博士的关系、示例对话。设定有版本，修改需博士确认。现有 DSH 的普瑞赛斯 personaPrefix 可作为普瑞赛斯人格的初稿来源。PRTS 的人格设定需新写。

**情感状态是持久化的状态量，不是每轮临时表演。**
- 每个人格维护自己的情感状态，以及对博士的关系状态。
- 状态由事件更新：对话内容、任务成败、长时间未见、博士的反馈。状态随时间回落。
- 状态影响措辞、语气、语音参数和是否主动开口。
- 状态不影响事实、计算结果、任务状态和权限判断。
- PRTS 的情感幅度低，普瑞赛斯的幅度高。
- 【待验证假设】具体的状态维度（例如愉悦度、唤醒度、关系亲近度）和更新规则，需要参考相关研究与开源实现后确定（§9）。

**事实规则高于角色表演。** 两个人格都必须：
- 区分工具结果与自己的推测；
- 不确定时明说；
- 受限时说明受限，不编造；
- 未执行的任务不能说成已完成。

**切换。** 博士用明确的指令切换人格。切换时由 PRTS 播报，切回时普瑞赛斯可以有告别语。切换不改变任务、权限和预算。

### 5.2 记忆与上下文总体架构：事件流 + 工作区 + 多存储记忆 + 后台巩固

博士 2026-10-29 认可此方向。设计参照人的认知机制，同时刻意避开人类记忆的缺陷。

```
感知（对话 / 工具结果 / 时间 / 文件变化）
        ↓
  事件日志（只追加，原始记录不可变）
        ↓ 实时写入               ↓ 空闲时巩固
  情景记忆 ←—— 关联图 ——→ 语义事实（双时间）
                                  技能 / 经验
  意图库（前瞻记忆）               主题目录（元记忆）
        ↓ 线索触发检索 + 扩散激活
  工作区（每轮渲染出的上下文，有预算）
   ├ 常驻：人格 / 关系状态 / 当前目标 / 主题目录
   ├ 当前对话窗口
   ├ 情景缓冲：本轮检索到的相关记忆（大意 + 原文引用）
   └ 工具说明（按需）
        ↓
  模型 ——（需要时）主动回忆工具 / 开子任务上下文
```

**借鉴的认知机制与对应设计**

| 认知机制 | 对应设计 |
|---|---|
| 工作记忆容量很小，靠组块承载信息（Cowan） | 工作区的常驻核心小而精，用组块化摘要承载大量信息 |
| 中央执行系统分配注意（Baddeley） | 上下文装配器按当前目标决定装入什么 |
| 海马快速记录、新皮层慢速形成知识、睡眠中重放巩固（互补学习系统） | 事件实时写入情景记忆；空闲时后台巩固为事实、关联与技能 |
| 线索触发回忆、扩散激活 | 检索由当前线索触发，沿关联图扩散，不只按向量相似度 |
| 前瞻记忆 | 意图库：时间或事件条件满足时触发 |
| 元记忆（知道自己知道什么） | 主题目录常驻工作区；记不清时如实说明，而不是猜 |
| 大意与原话分开存（模糊痕迹理论） | 工作区用大意，核实时回读原话 |
| 被打断后依靠线索接续 | 任务账本记录「停在哪里、下一步是什么」 |

**刻意不学的人类缺陷**：
- 回忆时改写记忆（再巩固导致的虚假记忆）。对策是原始事件不可变，巩固只生成带来源的派生条目。
- 编造细节。对策是结论必须有来源，没有来源的标为推断。
- 遗忘重要事项。对策是博士标记为重要的条目、前瞻意图和关键约束不参与自然遗忘。

### 5.3 记忆存储与过程

**存储（多存储，不只用一个向量库）**

| 存储 | 内容 | 取法 | 要求 |
|---|---|---|---|
| 事件日志 | 一切原始事件：对话原文、工具结果引用、时间与文件事件 | 按时间、来源、ID | 只追加；所有派生记忆都能追溯到这里 |
| 情景记忆 | 一段段经历：对话片段、任务经过、博士的情绪表达 | 时间、全文检索、语义、关联 | 保存原话与大意 |
| 语义事实 | 关于博士与世界的事实、偏好、项目知识 | 实体、全文、语义 | 区分博士明说与模型推断；有效时间与记录时间分开；冲突保留，不静默覆盖 |
| 关系记忆 | 每个人格与博士的共同经历和关系变化 | 按人格、时间、情境 | 按人格分开；供情感状态与主动回忆使用 |
| 技能与经验 | 做事方法、教训、反例与失效条件 | 按任务特征 | 候选与启用分开，经评估采用（§5.4） |
| 意图库 | 将来要做或要提醒的事，以及触发条件 | 按时间与事件触发 | 触发、完成、取消都有记录；不参与自然遗忘 |
| 主题目录 | 「我记得哪些主题、各有多少条、最近一次何时」 | 常驻工作区 | 由巩固过程维护；体积有上限 |
| 关联图 | 实体、事件、主题之间的联系 | 扩散激活 | 第一版可以只做实体共现关联，是否升级为完整图谱看召回实测 |

**过程**

- **实时写入**：事件发生即写入事件日志与情景记忆，不等会话结束。
- **后台巩固**：空闲时运行，主要做四件事：提炼事实、更新关系记忆、建立关联、更新主题目录与重要性；同时生成技能候选。有独立预算与额度上限，单独记账，可取消。
- **检索**：
  - 先由宿主确定可见范围；
  - 再综合时近性、重要性、与当前线索的相关度、与当前任务的相关度、关联扩散，计算一个排序；
  - 读取与展开仍独立判权。
- **重要性与遗忘**：每条记忆有重要性评分，影响排序与淡忘速度。情感强度高、博士明确强调、多次被有效引用的记忆更不容易淡忘。被检索次数本身不增加事实可信度。遗忘分三档：降低权重、退役（默认不检索）、清除（删除正文与派生副本，按 `DESIGN.md` §9 的流程执行）。前两档可逆。
- **主动回忆**：在相关情境中自然提起过去的事，频率受控，博士可以调低或关闭。
- **博士的控制权**：可以查看、纠正、删除任意记忆，删除覆盖检索索引、关联图与派生摘要。

**工作区装配（上下文）**

- **宿主装配为主，模型自管为辅。** 每轮由宿主按规则确定性地装配工作区。模型需要深挖时，调用主动回忆工具。不采用完全由模型自己换页的方案。
  - 【待验证假设】宿主装配比模型自管更可靠，第一版用同一组记忆测试对比确认。
- **装配顺序按稳定程度排列**：人格设定、主题目录等稳定内容在前，对话与检索结果在后，以提高模型提供方提示缓存的命中率。
- **预算**：输入预算 = min(配置上限, 模型窗口 − 输出预留 − 安全余量)。未知窗口不按无限处理。
- **压缩**：超限时先移除低相关材料与可回读的原文，再压缩旧对话。压缩结果保留指向原文的引用，不对旧摘要反复摘要。
- **工具结果卸载**：大结果存入对象存储，工作区只放引用、摘要与关键片段，需要时分页读取。
- **子任务上下文**：长任务的子步骤在干净的上下文中执行，只交回结论与产物引用，避免主工作区被污染。
- **跨会话连续**：新会话从任务账本、意图库、近期情景记忆与关系记忆重建「上次聊到哪里」，不把上一段聊天整体塞进来。
- **上下文清单**：每轮记录装入的材料、版本与预算用量，用于事后解释「她当时为什么这么说」。

**不进入第一版的方向**：
- StreamingLLM 类 KV 缓存技术；
- KV 持久化；
- 测试时学习（如 Titans）。

这些技术需要自有模型与权重，调用云端 API 时无法使用，归入冻结的研究线。解冻条件是 PRTS 稳定运行本地模型，且有记忆基准可以比较。

### 5.4 进化

目标：用得越久越懂博士，做事越熟练，同时不会变坏、不会悄悄改掉自己的底线。

第一阶段只做非参数进化，即不改模型权重：
- 积累经验 → 反思生成候选 → 隔离评估 → 版本化采用 → 运行观察 → 保留或回退。
- 可进化的对象包括：技能与做事方法、记忆检索与整理策略、上下文装配策略、人格措辞细节。
- 人格核心设定（身份、价值、禁忌、与博士的关系定位）的变更必须由博士确认后才能采用。
- 不可进化的对象：权限、预算上限、删除规则、评估器本身、事实规则。
- 评估使用独立样本；优化用的样本与最终检验用的样本分开；采用后检查原有能力是否退化（参照 `DESIGN.md` §10）。

第二阶段（冻结，另立研究线）：用博士授权的对话数据微调本地模型（如 LoRA），让人格更稳定、更像她自己。
- 解冻条件：第一阶段运行稳定；有可比较的评估集；本地硬件条件经实测确认。

## 6. 系统侧能力（PRTS 的本职）

沿用 2026-10-09 目标书的范围，这里只列对架构有约束的要求：

- **任务账本**：目标、输入、验收、预算、状态（完成、部分完成、等待输入、等待授权、失败、取消）、成果与证据引用。状态只能由执行结果和验收写入。
- **后台作业**：启动、查询、取消、恢复；中断后不重复已发生的外部效果。
- **工具**：统一登记格式（输入、输出、效果类别、所需能力、超时）；通过 MCP 接入外部工具。
- **科研**：计算保存输入、代码、参数、单位、环境；关键数值用解析式、基准或独立实现校验，不能用同一程序重跑代替。
- **日常**：资料整理、文档与表格、日程与待办、周期提醒。
- **入口**：终端界面（罗德岛风格）、语音（按键说话、播报、打断）。界面与核心通过接口通信，以后可增加其他终端。
- **运维**：健康面板、日志、备份恢复、升级与回退、插件兼容检查。

## 8. 边界与非目标

- 不主张意识、真实情感或自主意志。「像人」只按 §7 的行为验收判断。
- 部署假设为单用户、单机可信宿主。不做针对恶意管理员或同账号恶意进程的隔离证明，不做内核事件级观测。
- 语音不克隆原作声优或任何真人的声音；使用授权音色或自行调制的风格。
- 原作的角色与设定仅限个人使用；如果将来对外发布，需要另行评估版权问题。
- 多用户、商业运营不在范围内。
- 设备控制、网络运维、多终端同步属于完整产品阶段，不进入第一版（目标书 §四）。

### 9.1 Agent 循环的工具设计：优先借鉴 Claude Code

博士 2026-10-29 决定：Agent 循环里的工具设计优先借鉴 Claude Code。

【已核实】Claude Code 不公开源码。github.com/anthropics/claude-code 仓库只有插件、示例、devcontainer 与问题跟踪，LICENSE 声明为 Anthropic 专有；Anthropic 员工在该仓库 issue #1789 中说明不发布源码。npm 包 `@anthropic-ai/claude-code` 的许可写为「SEE LICENSE IN README.md」。

因此借鉴方式限定为：
- **只借鉴设计，不借鉴代码。** 依据是公开文档与可观察到的行为：工具划分、参数形态、工具说明的写法、权限模式、hooks、子代理、技能、项目记忆文件、上下文压缩。不使用 npm 包中混淆后的代码，也不使用任何泄露的源码。
- **实现层参照开源的同类项目**：codex（本地已有）、goose（本地已有）、opencode、pi（本地已有）。
- **Claude Agent SDK 需单独核查**：确认它是否开源、许可证是什么、是否只是封装 Claude Code 二进制。确认前不作为代码来源。

需要注意的差异：
- **工具说明与 Claude 模型的耦合。** Claude Code 的工具说明针对 Claude 模型调优过，PRTS 要支持多家模型提供方（§3）。工具说明需按模型验证，必要时为不同模型准备不同版本。
- **工具范围。** Claude Code 面向编程，工具集以文件、搜索、命令行为主。PRTS 还需要日常与科研工具，这部分 Claude Code 只能提供工具设计的风格参考。
- **权限归属。** Claude Code 的权限模式和 hooks 值得借鉴，但在 PRTS 中权限判定必须留在内核（§4.2），不能下放给插件。

审查时要回答的问题：
1. 哪些工具设计可以直接沿用：读、写、精确替换式编辑、文件名匹配、内容搜索、持久命令行、待办、子代理、网页获取。
2. 它的权限模式、hooks、子代理、技能、压缩机制分别对应 PRTS 的哪个内核服务或插件。
3. 开源同类项目中，哪一个的循环实现最接近这套设计，可以作为实现参考。
